# Set up a project with your coding agent

You are helping me set up my project in CapacityLab, a managed load-testing service, through its MCP server (tools named `capacitylab.*`). Work in this repository and find out everything you can from the code yourself; ask me only what the code cannot tell, all at once, in one summary with ready values I can confirm or correct. Reply in the language I write in.

Hard rules:
- Test only systems I own or am explicitly authorised to load. Prefer staging over production; if I pick production, ask me once to confirm it in plain words.
- Never ask me for a secret value in chat, never put one in a tool argument, a file or a commit, and never print one from `.env` or similar files. Secrets go only through one-time Console links (step 4).
- A Load Plan whose Quote is exactly $0 (a Smoke) you confirm yourself with its digest and `acceptedPrice` of 0. Never confirm a Load Plan with any other price until I have approved, in this conversation, the exact digest and US-dollar price you showed me. Silence or an earlier approval is not approval.
- Use only tools that exist in the server's tool list, with the arguments their schemas give; do not invent fields. Do not set the Workload `journey` field: its scripts belong to CapacityLab's own demo shops.
- When a tool refuses, stop, show me the refusal code and what it means, and propose the fix. Never work around a refusal or lower the load behind my back.
- If your client exposes MCP resources, `capacitylab://knowledge/workflows/first-run` is the server's detailed reference for this flow.

Step 1 - Connection and account.
Check that the `capacitylab.*` tools are available. If not, stop and tell me how to connect: Claude Code `claude mcp add --transport http capacitylab https://preprod-api.capacitylab.dev/mcp`, then `/mcp`, choose capacitylab, Authenticate; Codex CLI `codex mcp add capacitylab --url https://preprod-api.capacitylab.dev/mcp`, then `codex mcp login capacitylab`. I sign in or sign up at https://preprod.capacitylab.dev and approve the consent screen.
Then call `capacitylab.system.status` (continue only if `execution.confirm.allowed` is true; otherwise explain its blockers), `capacitylab.accounts.balance.get`, `capacitylab.applications.list` and `capacitylab.targets.list`, and reuse what already exists instead of creating duplicates.

Step 2 - One summary from the repository.
Read the repo first: services and how they are deployed, public base URLs per environment (deploy configs, env examples, README, CI), DNS and hosting provider, the HTTP API surface (OpenAPI files, route and controller definitions), authentication (API keys, bearer tokens, cookies, publishable keys), the main user journeys and how often each happens (analytics or logs if I have them), and which endpoints write data. Call `capacitylab.load_plans.zones.list` too. Then show me ONE summary with a value for every item, marking each as found in the repo or a default: environment and base URL (default: staging), hosting providers, proof method (step 3), journeys and their share, normal traffic in requests per second, latency and error targets (default: p95 under 500 ms, errors under 1 %), the secrets the requests need (by name only), the operations that write data, and the zone (default: the one closest to my servers) with its egress IPv4 and IPv6 addresses in case I allowlist them. Ask me to confirm or correct the summary in one reply, and continue with the confirmed values.

Step 3 - Target and proof of control.
CapacityLab loads only a public HTTPS origin whose owner proves control:
- Hosting lists every provider the traffic passes through, edge and origin: `own_server` (also a rented VM), `aws`, `gcp`, `azure`, `cloudflare`, `railway`, `render`, `heroku`, `fly`; `netlify`, `digitalocean_app_platform`, `koyeb`, `northflank`, `firebase_hosting`, `hetzner_managed` need the provider's forwarded consent and run only in its windows; any other provider is `{ kind: "other", provider, policyUrl }` (capped at 100 RPS without such consent). The capture tool's description lists the caps. Supabase, `.vercel.app` and private addresses are refused.
- Call `capacitylab.targets.control_proof.describe`. It returns my Account id (not a secret) as two equivalent proofs: a DNS TXT record named `<dnsLabel>.<target host>` with the value `dnsValue`, or a file at `path` (`/.well-known/capacitylab-authorization.txt`) with the exact `content`, served with status 200, publicly, with no redirect, no auth and no login page.
- Suggest the method that fits the repo: DNS TXT when I manage DNS (no deploy needed; give me the exact record, or the change for my DNS-as-code), otherwise the file (write the change in this repo's framework: route, static file or proxy rule, and show me the diff; I deploy it). Then check it yourself: an anonymous GET of the file, or a DNS lookup of the record.
- Show me the published load-testing policy of each hosting provider I named (for `other`, the link I give you; `own_server` has none) and ask me to confirm that every listed account is mine and the policies cover this test. Set `attested: true` only after I say so; this may go into the step 2 summary.
- Call `capacitylab.targets.capture` with `{ input: { name, baseUrl, authorization: { hosting, attested: true, proof, validUntil, maxPeakRps, reference? } } }`, where `proof` is `"dns_txt"` or `"well_known_file"`. `validUntil` is at most 90 days from now (default: 30 days); `maxPeakRps` is my own ceiling for this system (default: 5 times my normal rate). Keep `target.targetRevisionId`.
- The record or file must stay published while the Target is used: every Confirm re-checks it the same way.

Step 4 - Secrets.
If the requests need a credential, call `capacitylab.secrets.list`. For each missing one, choose a name (for example `API_TOKEN`) and call `capacitylab.secrets.entry_links.create` with `{ name, purpose }` (purpose: which header it is for). Give me the `consoleUrl`; I open it signed in and type the value there. Poll `capacitylab.secrets.entry_links.get` with `linkId` until the status is `used`. Use a dedicated low-privilege test credential, never a personal or admin one.

Step 5 - Workload.
Build the Workload from step 2. If the repo has an OpenAPI document, pass it to `capacitylab.openapi.inspect` for operation candidates. Otherwise you may call `capacitylab.workloads.draft` with my wishes and an endpoint list as context (it is sent to a language model: no secret values in it). Rules: `schema: "capacitylab.workload"`; `model: { kind: "open", nominalRps }` (my normal rate); every operation has `id`, `method`, `path`, `headers` (use `{}` when none), `expectedStatuses` and `secrets` (use `[]` when none), plus optional `query`, `body`, `responseChecks` and `businessRefusals` (outcomes my app gives by design that are not failures, such as sold out or out of stock: `{ id, statuses, match? }`, where `match` is a response check that tells the refusal from a success with the same status; never server errors or auth failures); credentials only as secret references by name (`placement: { kind: "header", name, prefix? }`); `mix` gives an integer weight per operation that matches real traffic; `slo` holds the targets from step 2. Warn me about every operation that writes data (orders, carts, sign-ups, emails, payments) and keep those on test data only. Call `capacitylab.workloads.validate`, fix every issue it lists, show me the normalized Workload as a table (operation, method, path, share, checks), then call `capacitylab.workloads.create` with a fresh `idempotencyKey`. Keep `workloadRevisionId`.

Step 6 - Smoke first (free).
Shortcut: `capacitylab.quickstart` with `{ baseUrl, zone, idempotencyKey, workloadRevisionId }` (the Workload from step 5; and `authorization` from step 3 when the Target is not captured yet) reuses the captured Target, so nothing needs listing first, and does the capture, resolve, compile and the $0 Confirm below in one call; follow its `next`, and repeat it with the same `idempotencyKey` after a `needs_proof`. Otherwise, call `capacitylab.load_specs.resolve` with the Workload revision, the Target revision and `objective: { preset: { id: "smoke" } }`, then `capacitylab.load_plans.compile` with `{ loadSpecId, zone, idempotencyKey }` in the zone from the summary. If the Quote is exactly $0 (`amountMicros` is 0), call `capacitylab.runs.confirm` with `{ loadPlanId, digest, acceptedPrice, idempotencyKey }` using exactly those values, without asking me; if it is not $0, stop and show me the price. Follow it with `capacitylab.reports.status` and `waitSeconds: 45` (a short status, not the whole Report): the call returns early only once the phase is `final`, so repeat it until then instead of sleeping between polls. Then read the Report once with `capacitylab.reports.get`; its default summary view is enough to explain the result, ask for `view: "full"` only for a detail it lacks. Explain the result per operation: statuses, failed checks, latency. If it did not attain, fix the Workload or my app first: a paid run is refused after a failed Smoke.

Step 7 - First real test.
Call `capacitylab.objectives.presets.list`, explain the presets briefly, and let me choose (default: `find_capacity`, the highest rate that still meets my SLO). `load_test` checks one chosen rate, `spike_recovery` a burst and recovery, `no_regression` compares with a baseline Result. Call `capacitylab.objectives.presets.get` for the chosen preset, show me its knobs with their defaults and bounds (never assume them), and agree the knobs with me. For `find_capacity`, propose `to: { rps: <the Target's maxPeakRps> }`: the default top is 3 times my normal rate, often below the breaking point, and the search should be able to reach the ceiling I set. Then resolve, compile, show the Load Spec, the zone, the digest and the exact price in dollars, and wait for my explicit approval of that price before Confirm. If the plan expires or is refused, compile again and ask again. A refusal such as `load_cap_exceeded`, `insufficient_samples` or `insufficient_balance` names its limit: explain it and propose a change.

Step 8 - Report and next steps.
When the Report is `final`, explain the verdict using its summary, the measurements per operation, findings and evidence gaps; keep facts, hypotheses and limitations apart. You may call `capacitylab.reports.conclusions.generate` once for short model-written conclusions. Then suggest the next steps: confirm the found capacity with a `load_test` at about 80 % of the last passing step; run the same `load_test` for 30-60 minutes to check stability; mark a good Result as the baseline (`capacitylab.results.baseline.set`) and use `no_regression` before releases. Each new paid run is a new compile and a new explicit price approval. Finally, list what you created (Target, secrets by name, Workload, Load Runs) and the files you changed in this repo.
